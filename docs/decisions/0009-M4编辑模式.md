# ADR-0009 · M4 编辑模式：人工标注 + LLM 改谱 + 程序校验

- 日期：2026-08-13
- 状态：已接受
- 决策人：洛怜（拍板交互对话式闭环 + LLM 直接改谱 + 规则/标注执行器）& Teto（M4-CLOSE-LOOP 实现）

## 背景

M3 完成双后端（GAME 成品歌 + RMVPE 哼唱），M4 = 人在环迭代：音乐对话闭环（解析 → 回放 → 标注/反馈 → 修正 → 收敛）。
关键问题：**LLM 能不能直接改谱？** 修正执行器怎么做才稳？

## 备选方案

1. **规则解析 LLM 建议文本**（LLM 输出"把第 5 音升半音"类自然语言，程序解析）——脆弱，解析即地狱
2. **LLM 直接输出修正后的完整音符 JSON 数组**（Note/Score 全是 dataclass + JSON，音符数组对 LLM 最友好）——M4 定案
3. **人工标注 + LLM 混合**：用户明确指出的音由程序直接应用（确定性、最高优先级、不经过 LLM）；LLM 只处理自然语言反馈与音乐性建议

## 决策

1. **编辑模式（创作辅助）与评估模式（LLM 只读，ADR-0004/0005）并存**：评估公平性约束 ≠ 创作辅助，两个模式都保留
2. `tsov/analysis/edit.py`：`edit_score(score, feedback, annotations, llm) -> EditResult`
   - 人工标注先行（pitch/delete/add/merge，程序直接应用，LLM 不得覆盖标注结果）
   - LLM 编辑：音符表 + 用户 feedback + stage-03 suspicious_notes → 输出**完整修正音符 JSON 数组**
   - 程序校验层：JSON 解析失败/缺字段/pitch 越界/start>=end/空数组 → 拒绝，保留原谱（LLM 失败不阻塞）
   - diff_summary：人类可读（+新增 / ~改音 / -删除 / ~改时长），最多 20 条
3. 标注的 `pitch` 编辑：pitch_hz=midi_to_hz(新值)、deviation_cents 置 0（编辑语义下简化）

## 影响 / 实测

- **LLM 改谱能力结论（M4 演示实测）**：能输出合法完整音符 JSON 数组、能理解语义反馈；但**机械精度不可靠**——
  "加 E4 起音 + 整体 +12 半音"两次提示词都给出非均匀移位（+8~+22st）且把 E4 加在末尾 → **精确操作走人工标注兜底**（demo A 用标注确定性达成 16 音 E4+全部+12），LLM 留给音乐性/语义建议
- demo B 验证"标注最高优先级"：标注 D#3→D3 落定后 LLM 不覆盖
- 演示产物：`output/m3-closed-loop/2026-08-13/m4-demo-{hum04,hum05}/`（edit-score + song.mid + song.wav + diff + README）
- 遗留：LLM 精确操作（定点插入/统一移位）不可靠的根因是推理模型"音乐性优先"；后续可加"结构化指令模板"（如 JSON 操作指令而非自然语言）试点，或直接用标注 DSL
